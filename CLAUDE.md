## Project

This is the Supply Chain Early-Warning Tool: it flags SKUs at risk of stockout or overstock, explains each flag in plain language via an LLM call grounded in that SKU's real numbers, and answers free-text questions from the same underlying data.

## Non-negotiables

These override convenience or speed. If a change would violate one of these, stop and flag it instead of proceeding.

- **Never template LLM explanations.** Every flag explanation is generated by an LLM call at runtime, built from that SKU's actual computed numbers (stock, demand trend, lead time, days of coverage). No hardcoded strings, no f-string templates dressed up as "explanations."
- **Every threshold is a formula with a stated reason, not a bare constant.** `if coverage_days < 7:` needs a comment explaining why 7 and not 5 or 10 — tied to lead time or the cost of a false alarm vs. a missed flag.
- **New SKUs (~2 weeks of history) never silently use established-SKU thresholds.** They use whatever fallback approach is recorded for them in `docs/DECISIONS.md` — if that entry is still empty, resolve it there first instead of guessing inline.
- **The Q&A box retrieves data before calling the LLM.** Never let the model answer from its own guess about the data — fetch the relevant SKU rows first, then pass them into the prompt.
- **Missing `units_sold` values and category-casing normalization follow the rule recorded in `docs/DECISIONS.md`**, not an ad hoc choice made mid-implementation. No entry yet? Decide, record it, then implement — don't implement first and back-fill the reasoning.

## Before marking a flagging or explanation feature "done"

- The flag fires (or correctly doesn't) for at least one established SKU and one new SKU.
- The LLM explanation for a flagged SKU cites numbers that actually match that SKU's row — spot-check at least two, don't assume.
- The Q&A box answers a real free-text question, grounded in retrieved data, not generic text.

Full checklist: "Before You Ship, Verify" in `docs/BUILD_BRIEF.md`.
