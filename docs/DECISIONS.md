## Data Preparation

- **`units_sold` gap rule (impute vs. exclude)**: Short gaps of ≤2 consecutive missing days within a SKU's series are linearly interpolated (bounded — never extrapolated past the first/last known value). Longer gaps are left as missing and excluded from demand statistics rather than guessed at. Rationale: 2 days is short enough that linear interpolation between real neighboring readings is a reasonable estimate of a smooth demand process; beyond that, an interpolated value starts asserting more confidence than the data supports, and a wrong guess would bias safety-stock sizing.
  - Implementation: `interpolate_demand_gaps()` in [core/data_pipeline.py](../core/data_pipeline.py), `s.interpolate(limit=2, limit_direction="both", limit_area="inside")`.
  - **Bug found and fixed this session**: `clean_and_deduplicate()`'s aggregation step used `.agg({"units_sold": "sum"})`, and pandas' `sum()` silently returns `0.0` (not `NaN`) for an all-NaN group. Every one of the 90 genuinely-missing `units_sold` rows in the raw CSV was being converted into a verified zero-sales day *before* the interpolation step above ever ran — so the documented rule was never actually executing. Fixed by aggregating with `sum(min_count=1)`, which preserves `NaN` when a group has no real values. Verified: post-fix, 89 of the 90 originally-missing rows are correctly bounded-interpolated and 1 (a longer gap) correctly stays excluded, matching this rule for the first time.
  - Consequence of the bug: safety stock, reorder points, and the backtest were all computed on data with those 90 days silently understated to zero. Re-running after the fix shifted flagged-SKU counts (11 → 10 flagged of 28) and backtest recall (74.2% → ~73.5%) — small shifts, but the pre-fix numbers were measuring a demand series that didn't match the real data.

- **Category-casing normalization rule**: Lowercase (casefold) + collapse repeated whitespace. `Snacks` / `SNACKS` / ` snacks ` all normalize to the same key.
  - Implementation: `normalize_category_key()` in [core/data_pipeline.py](../core/data_pipeline.py). Verified against the actual CSV: all 10 raw category strings collapse cleanly into exactly 5 categories (Snacks, Beverages, Sugar, Pasta, Flour).
  - **Scope decision**: no fuzzy-matching for near-duplicate spellings (e.g. `Snack` vs `Snacks`, or a typo) is implemented. This dataset has no such near-duplicates once case/whitespace are normalized, so there's nothing to validate it against, and adding fuzzy-matching now would be unvalidated complexity for a case that doesn't currently exist. If a future data refresh introduces spelling variants, this should be revisited rather than assumed away again.

- **Lead-time validation rule**: A `lead_time_days` value is distrusted if it falls outside `[1, 60]` days (i.e. zero/negative, or implausibly long for an FMCG supplier). A distrusted or missing value is replaced with that SKU's own median lead time; if the SKU has no valid lead time at all, falls back to the dataset-wide median.
  - Implementation: `sanitize_lead_times()` in [core/data_pipeline.py](../core/data_pipeline.py).
  - Verified two ways: (1) the current dataset has zero values outside `[1, 60]` (all lead times fall in 3-14 days), so this path doesn't currently fire in production; (2) confirmed the fallback logic itself works by injecting synthetic bad values (999, 0) and checking they get replaced with the correct SKU median.
  - The `[1, 60]` bound itself: reasoning unclear beyond "generously wide but excludes obviously broken values (0, negative, or triple-digit typos)" — not tied to a specific supplier contract or observed outlier, since this dataset doesn't contain one to calibrate against.

- **Missing `closing_stock` rule** (not explicitly asked in the brief, but a real gap found in the audit): forward-fill the last known on-hand count within a SKU's series. A missing reading means the count wasn't taken that day, not that stock reset to zero or became unknown going forward — physical inventory doesn't vanish between counts. Bounded inside the series (no fabricating a stock level before a SKU's first real reading).
  - Implementation: `fill_closing_stock_gaps()` in [core/data_pipeline.py](../core/data_pipeline.py), added this session. Raw values preserved in `closing_stock_raw` for lineage. Verified: all 45 originally-missing `closing_stock` rows are filled; before this fix they stayed `NaN` indefinitely with no documented rule, which was a latent crash risk for `score_sku_inventory()`'s `group.iloc[-1]["closing_stock"]` lookup if a SKU's most recent reading was ever missing (not currently the case, but undocumented and unguarded).

## Model Selection & Validation

- **Approach chosen**: Hybrid reorder-point / stochastic safety-stock system — not a trained ML forecasting model. Blended median+EWMA daily velocity, day-of-week seasonality applied over the lead-time horizon, safety stock combining demand variance *and* lead-time variance (not just demand variance), ABC-tiered service levels (z-scores 2.05/1.65/1.28 for A/B/C).
- **Why it fits this data**: ~6 months for established SKUs is enough to estimate a stable median/EWMA velocity, day-of-week pattern, and demand variance per SKU — but not enough to responsibly train and validate a general-purpose forecasting model per SKU. ~2 weeks for new SKUs is far too little for *any* per-SKU statistical model; a reorder-point formula that borrows a category-level CV prior (see New vs. Established SKUs below) degrades gracefully where a trained model would have nothing to train on.
- **Evaluation metric and validation method**: Rolling-origin walk-forward backtest (`core/backtest.py`) — at each historical date *t*, demand/volatility are computed strictly from data available at *t-1* (1-day-lagged rolling stats), preventing lookahead leakage that a random train/test split would introduce given hourly/daily autocorrelation. Target event: did an alert fire before an actual stockout occurred within the SKU's lead-time horizon? Metric: precision/recall/F1, reported alongside accuracy and false-alarm rate rather than accuracy alone, because the classes are imbalanced (true negatives — healthy inventory days — vastly outnumber actual stockouts).
  - Current results (re-run after the `units_sold` fix, on 3,926 checkpoints): **recall ≈ 73.5%, precision ≈ 18.4%, F1 ≈ 29.5%, accuracy ≈ 60.0%**. Recall is prioritized deliberately (see Risk Thresholds below) — precision is low by design, not by accident, but that tradeoff was, until this session, only asserted in a UI caption, not written down anywhere as a decision.

## Risk Thresholds & Formulas

- **Stockout trigger**: `stock <= reorder_point OR days_coverage <= lead_time * (1 + 0.5*CV)`, suppressed if a recent receipt (last 7 days) has already pushed stock back above safety stock. Widening the lead-time comparison by `0.5*CV` means a more volatile SKU gets flagged earlier relative to its lead time than a stable one — intentional, since volatility is exactly what erodes a fixed buffer fastest.
- **Overstock trigger**: `days_coverage >= coverage_limit AND stock > 1.5 * reorder_point` — requires *both* excess days of coverage *and* a meaningful multiple over the reorder point, so a SKU isn't flagged overstock purely for sitting just past its coverage limit while still reasonably close to its reorder point.
- **False-alarm vs. missed-flag tradeoff**: A missed stockout (false negative) halts a production line; a false alarm (false positive) costs a few minutes of an operator's review time or an order placed slightly early. Given that asymmetry, the system is deliberately tuned toward high recall over high precision — reflected in the backtest results above (73.5% recall, 18.4% precision) and in ABC-tiered service levels that push Class A (top 70% volume) service level to 98% (z=2.05). This tradeoff was previously only stated as an assertion in a UI caption ([ui/backtest_view.py](../ui/backtest_view.py)) with no specific cost multiplier behind it; recorded here as the actual operating decision, without inventing a false-precision cost multiplier (e.g. "10-50x") that isn't derived from any data in this repo.

## New vs. Established SKUs

- **Where the established approach fails on ~2 weeks of data**: a per-SKU standard deviation from 12-14 observations is not a trustworthy demand-volatility estimate — a single unusually large or small day swings it heavily. Using it directly in the safety-stock formula would produce either wildly oversized or undersized buffers depending on luck of the draw in those first two weeks.
- **Fallback approach for new SKUs**: `is_new = history_days < 56`. New SKUs (1) inherit their category's median coefficient of variation (computed only from established SKUs with ≥56 days of history, `compute_category_priors()`) rather than trusting their own thin-sample CV, (2) get a wider safety-stock floor (`max(daily_demand * 0.50, ...)` vs. `0.25` for established SKUs) reflecting genuine extra uncertainty, and (3) use a tighter overstock coverage limit (21 vs. 28 days — see `config.py` for the lead-time-tied reasoning) since their velocity estimate is less trustworthy.
  - Implementation: `calculate_stochastic_safety_stock(..., is_new=...)` in [core/inventory_engine.py](../core/inventory_engine.py).
  - Verified live: SKU-2000/2001/2002 (12 days of history each) all correctly score with the `launch baseline (... cat CV ...)` method label distinct from established SKUs' `full-history baseline`, and correctly flag "Order soon" — genuinely, since these 3 SKUs actually sit at 0 closing stock in the raw data with no receipts yet.
- **How thresholds are set without 6 months of reference data**: by borrowing from the *category*, not the individual SKU — a new Snacks SKU inherits the empirical CV computed across all established Snacks SKUs, on the assumption that demand volatility is more a property of the product category (impulse buy vs. staple, perishable vs. shelf-stable) than of the specific SKU's brief history.

## Risk Classification

- **Action buckets**: `Order soon` (stockout trigger, coverage ≤ lead time), `Plan replenishment` (stockout trigger, coverage > lead time but still within the widened trigger band), `Overstock risk`, `Monitor closely` (demand-surge trigger only, no stock trigger), `On track` (no trigger). Assignment is a plain if/elif chain in `score_sku_inventory()` ([core/inventory_engine.py](../core/inventory_engine.py)) — deliberately not a black-box score threshold, so an operator (or another engineer) can read the exact boolean condition that put a SKU in its bucket.
- **Composite 0-100 risk score**: a separate, continuous severity signal layered on top of the buckets (coverage depletion 35%, demand acceleration 25%, demand volatility 20%, reorder proximity 20%, ABC-multiplied). Used for sorting/severity color, not for bucket assignment — the bucket a SKU lands in is always explainable by its own trigger condition, independent of the score.
- **Known calibration gap** (found this session, not fixed — see `config.py` `SEVERITY_THRESHOLDS` comment): a SKU that is already overdue with same-day stockout can still score below the 75-point "Critical" cutoff (e.g. a verified case in this dataset scores ~74 and displays as "High"). Documented rather than silently adjusted, since changing the cutoff changes which SKUs are labeled Critical across the whole app, CSV export, and alert digest — a modeling decision, not a bug fix.

## Grounding the LLM

- **Exact figures passed into the explanation prompt**: stock, daily demand, forward lead-time demand, days of coverage, lead time (+ std dev), reorder point, safety stock, recommended order quantity, order-by/stockout dates, demand trend %, coefficient of variation, ABC class, risk score/severity/bucket. Full list: `build_sku_facts()` in [ai/grounding.py](../ai/grounding.py).
- **Check used to catch an ungrounded explanation before the user sees it**: `validate_grounded_numbers()` extracts every number the LLM's response cites and requires each to be traceable (within 1% or 0.5 units) to a number actually present in the evidence passed into that prompt — either a structured fact or a number embedded in an evidence string (e.g. "8 days" inside a timing message). If a live response fails this check, it's discarded and the deterministic local explanation is shown instead, with a warning explaining why.
  - **This function existed in the codebase before this session but was never called anywhere** — dead code satisfying the letter of "we have a check" with none of the substance. Wired into `explain_sku()` and all four routes of `answer_agentic_question()` this session.
  - Wiring it in surfaced three real bugs in the check itself that would have made it reject *correct*, grounded output almost 100% of the time if left as originally written: (1) it never accounted for Groq's use of Unicode dash variants (e.g. `2026‑06‑26` with a non-breaking hyphen) in dates, so a correctly-cited date's digits never matched the evidence's plain-ASCII date string; (2) it read the digits inside a SKU code itself (`SKU-1010` → `1010`) as an uncited numeric claim; (3) it never accounted for Groq formatting large numbers with a narrow no-break space as a thousands separator (`2 190.4`), which split into two wrong numbers under the original digit-only regex. All three fixed and reverified against live Groq output across SKUs and Q&A routes before shipping.
- **Q&A retrieval logic**: `answer_agentic_question()` routes a free-text question through 4 patterns, checked in order: (1) a `SKU-####` pattern in the question → filter `scores` to that one row; (2) a known category name/plural mentioned → filter to that category's SKUs; (3) "class a" / "pareto" / "top priority" language → filter to ABC-A SKUs; (4) anything else → fall back to the general flagged-SKU queue (urgency > 0, top 10). Whichever subset is selected, only that filtered data is serialized into the LLM prompt — the model never sees the full portfolio or is asked to answer from unstated general knowledge.
- **Model identity shown to the user must be the model that actually answered, not an assumed one**: found this session that every UI surface (sidebar, chat caption, SKU-detail caption, source label, footer) hardcoded "Llama-3.3-70B," regardless of which model actually generated a given response. The real configured primary model is `DEFAULT_GROQ_MODEL` in `config.py` (`openai/gpt-oss-120b` by default) — Llama-3.3-70B is only one of several *fallback* candidates in `GROQ_FALLBACK_MODELS`, tried only if the primary and earlier fallbacks are unavailable. Fixed by having `execute_groq_chat()` return the actual `model` id that answered on `LLMResult.model`, and updating every display site to show that value instead of a hardcoded string. Verified live: the SKU-detail source label now reads "Live Model Explanation (openai/gpt-oss-120b)," matching the configured primary model.

## Tool Structure

- **At a glance** (top of the Attention Queue tab, no clicks): total flagged count vs. portfolio size, critical severity count, Class-A-at-risk count, total reorder units (hero banner + KPI cards), plus 3 portfolio-level charts (risk donut, ABC volume bar, stockout countdown).
- **One click away**: per-SKU deep dive (stock trajectory, demand/receipts chart, risk gauge, what-if simulator, AI explanation, full evidence table) via the SKU-detail tab's selector; free-text Q&A via its own tab; backtest/validation evidence via its own tab. The three-tier structure (glance → filtered table → single-SKU drill-down) means a business user never has to understand the underlying formulas to use the top level, but every number is traceable to its formula for someone who clicks through.
